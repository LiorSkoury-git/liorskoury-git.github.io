A reusable Digital Twin system

A design becomes thousands of physical actions. This research branch follows those actions through manufacturing, then turns their shared task record into a Digital Twin architecture that can work with different machines and processes.

01 / Digital to physical handoff

Meaning shifts as work moves between digital and physical spaces. In a digital environment, an activity may appear as a single data element or an abstracted action. In physical space, carrying it out can require a sequence of movements, tool changes, actuations, and human interventions. The first step in this research was therefore to establish a common ground between the two spaces: the concept of a unified task, which connects the digital description to its physical execution.

02 / The first working thread

The first study to apply the unified task concept was the livMats Biomimetic Shell. It showed how a shared task structure could connect design intent and individual elements to the machines, tools, and actions involved in making them. The resulting data could then be analysed while remaining traceable to both the digital design and its physical execution.

03 / A reusable system

The next step asked which parts of the Digital Twin could remain the same as building systems and fabrication environments changed. Tasks and their histories form the data core, linking design elements, machines, tools, and execution outcomes across two databases: one for project records and monitoring, and a local one for execution. A virtual actor represents each machine, translating the shared task structure into its own communication protocol and returning feedback. Modular services use that feedback to visualise progress, simulate or predict outcomes, and add tasks as work unfolds. An event-driven engine coordinates these exchanges, allowing machines to work in sequence or in parallel while maintaining a coherent record.

04 / Implementation and validation

The architecture was examined in three process modes. Its task-based data model and execution engine remain consistent, while virtual actors and services adapt to how each process is planned, carried out, and adjusted.

Mode 1 / A fixed sequence of tasks

All tasks are defined before fabrication begins and executed in a set order. The Digital Twin sends instructions to the robot, monitors completion, and records each outcome before the sequence advances. Feedback supports the analysis and planning of later work without changing the current sequence.

This mode was tested in the livMatS Biomimetic Shell. An industrial robot equipped with three tools executed a predefined task sequence, while a visualisation service displayed its progress.

Mode 2 / Tasks generated from feedback

The full task sequence cannot be specified in advance. Instead, each action’s outcome and the current state of the work inform what should happen next. The Digital Twin uses this feedback to generate and coordinate tasks as construction progresses.

This mode was tested in a collective robotic construction study involving eight mobile RADr robots and a Vicon tracking system. An agent-based model service generated behaviour for each robot. Services connected to the tracking system queried its data, injected tasks, and streamed the evolving process state to users.

Mode 3 / A planned action with live adjustments

The overall action space is defined in advance, but operating parameters can change during execution. The Digital Twin monitors the machines and adjusts their control while work continues, without interrupting the planned actions.

This mode was tested in a large-scale 3D printing process involving an industrial robot and a material pump. Each machine was paired with a task-injection service that queried its data and a control service that used the data to adjust its operation. A further visualisation service streamed the process state to users.

05 / What this establishes

Across the three implementations, the research shows how a shared task-based architecture can support different ways of making. The same data model and execution engine coordinated a fixed assembly sequence, tasks generated through feedback, and continuous printing with live adjustments. Virtual actors connected machines and sensors to the system, while local and external services used their data to monitor progress, generate tasks, and adjust execution. In each setting, the task record linked digital representations to physical actions and their outcomes.

That record creates a basis for using fabrication data beyond the project in which it was collected. Task histories could inform later planning and prediction, while libraries of virtual actors and services could make the architecture easier to apply to new machines and processes. The same structure could also support physical AI: it offers a way to organise tasks, observations, and outcomes as data for vision-language-action (VLA) models, and a task interface for connecting existing models to physical execution.
